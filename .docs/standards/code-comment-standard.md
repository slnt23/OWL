## 背景与目标

本文档约束 OWL 仓库中的代码注释，目标是让注释解释“为什么”和“约束条件”，而不是复述代码本身。注释与代码同 PR、同评审、同维护要求。

## 强制规则

1. 禁止提交被注释掉的旧代码、旧 SQL 和旧配置。需要保留的历史由 Git 管理。
2. 注释使用中文，代码标识符、命令和专有名词保留英文。
3. 公开 API（Controller、Service、公共工具类）使用 Javadoc 说明用途；`@param` 和 `@return` 只在信息有意义时保留，禁止空参数说明。
4. DTO/VO 字段使用 `@Schema(description = "...")` 描述，不重复添加 `//` 字段注释。
5. 行内注释只写“为什么这么做、有什么边界条件”，不写“这行代码在做什么”。
6. 多步骤方法可以保留简短步骤注释，例如 `// 1. 校验验证码`；单行代码不逐行加注释。
7. TODO 统一写成 `TODO(负责人或主题): 具体事项`，禁止使用“后续再说”“待补充”等模糊记录。
8. Mapper XML、YAML 和 POM 中禁止用注释保存备选实现；功能开关使用 profile 或环境变量。

## 建议

- 方法名和变量名已经表达含义时，可以省略注释。
- 复杂业务决策优先写入 `.docs/adr/`，代码注释只放最关键的约束。
- 新增或修改业务模块时，Controller 和 Service 至少保留类级 Javadoc。

## 验证

- 合并前检查提交内容不包含“被注释掉的代码块”。
- 代码评审时确认注释没有空参数、模糊 TODO 和重复字段说明。
- 批量清理时可使用脚本匹配 `^\s*//` 后跟代码形态内容的行。
