# OWL 文档编写规范

| 属性 | 值 |
| --- | --- |
| 状态 | 已批准 |
| 负责人 | 仓库 Owner |
| 创建时间 | 2026-08-03 |
| 更新时间 | 2026-08-16 |
| 适用范围 | 仓库根目录 README 与 `.docs` 下全部文档 |

## 1. 目的

项目变大后，文档是团队共同的记忆。本规范用于保证文档可读、可查、可评审、可维护，并让文档变更像代码变更一样受到约束。

本规范是强制要求。表述使用“必须”“禁止”时不可妥协；使用“建议”时可按场景取舍，但偏离需要有明确理由。

## 2. 核心原则

1. 文档即代码：文档与代码同仓库、同 PR、同评审、同质量要求。
2. 读者优先：先写清楚读者、目的和结论，再展开细节。
3. 单一事实来源：事实只在一处维护，其他位置通过链接引用。
4. 最小必要：一份文档必须值得维护；内容越少，维护成本越低。
5. 准确优先：过时文档是缺陷，行为变化必须同步更新相关文档。
6. 安全合规：文档不得包含密钥、口令、Token 或真实个人信息。
7. 可追溯：状态、负责人、日期、相关代码和链接必须可追查。

## 3. 文档分类与目录

`.docs` 顶层目录使用英文命名：`adr`、`database`、`design-standards`、`others`，职责如下：

| 分类 | 位置 | 内容 | 什么时候需要 |
| --- | --- | --- | --- |
| 文档中心 | `.docs/README.md` | 文档地图、职责边界、生命周期 | 长期存在 |
| 架构决策 | `.docs/adr/` | ADR，记录决策背景、方案、后果 | 重大架构或设计决定时 |
| 数据库 | `.docs/database/` | DDL、迁移脚本、示例数据 | 表结构或数据规则变化时 |
| 设计规范 | `.docs/design-standards/` | 代码设计方案、代码注释规范、文档编写规范 | 新增或修改规则时 |
| 其他文档 | `.docs/others/` | 接口联调、开发手册、运维文档、图片素材 | 对外接口或操作流程变化时 |
| 变更记录 | 根目录 `CHANGELOG.md` | 面向使用者的版本变更 | 每次发布时 |

如果现有分类无法容纳内容，先新增分类并在 `.docs/README.md` 登记，不要放入不相关目录。

## 4. 文件命名

1. `design-standards` 目录内文件名使用小写 kebab-case 英文，例如 `code-comment-standard.md`；其余文档文件名使用中文。
2. 文件名不使用版本号或日期；历史由 Git 管理。
3. ADR 使用 `ADR-XXX-中文标题.md`，编号连续且不重复，例如 `ADR-005-财神理财模块设计.md`。
4. 故障处理文档使用 `故障处理-目标-场景.md`，例如 `故障处理-MySQL-重启.md`。
5. 一份文档只讲一个主题；超过 500 行或受众不同时应拆分并互相链接。
6. 每个顶层目录文件较多时，使用该目录的 `README.md` 或中文索引文档作为入口。

## 5. 文档结构与元信息

### 5.1 元信息

ADR、设计说明、运维文档和规范类文档必须在标题后放置元信息表：

```markdown
| 属性 | 值 |
| --- | --- |
| 状态 | 草稿 / 评审中 / 已批准 / 已废弃 |
| 负责人 | 模块或团队 |
| 创建时间 | 2026-08-03 |
| 更新时间 | 2026-08-03 |
| 适用版本 | 全部 / 具体版本 |
```

状态变更必须更新元信息，并在文档末尾补充变更历史。

### 5.2 通用结构

正式文档按以下顺序组织：

1. H1 标题，唯一且概括主题。
2. 元信息表。
3. 背景与目标：说明为什么存在、给谁看。
4. 正文：按读者任务组织，先结论后细节。
5. 变更历史：日期、变更内容、负责人。
6. 相关文档：相对链接。

非正式文档（如目录索引、简短说明）可以省略元信息表，但开头必须说明读者和用途。

### 5.3 ADR 结构

ADR 必须包含以下小节，与现有 `ADR-001` 至 `ADR-005` 保持一致：

- `状态`：已采纳、已废弃、提案中等。
- `背景`：问题、约束和触发原因。
- `决策`：每个决策点写明“选择、原因、备选”。
- `后果`：正面与负面影响、维护责任。
- `待定`（可选）：尚未决定、后续需要验证的事项。

ADR 不记录日常排期和琐碎变更；只记录影响维护的架构决策。

## 6. 写作要求

### 6.1 语言

1. 正文以中文为主；代码、命令、字段、文件名和专有名词保留英文。
2. 术语首次出现时给出中文说明，例如“网关（Gateway）”。
3. 使用主动语态和短句，一句话只表达一个事实。
4. 使用“必须”“禁止”表达强制规则，使用“建议”表达推荐做法。
5. 不使用“我们”“大家”“好的”“麻烦”等对话或口语表达。
6. 不使用表情符号、感叹号堆叠、营销化措辞和夸张形容词。
7. 禁止把聊天记录、AI 问答原文或会议流水账直接放入正式文档；先提炼结论。
8. 避免“尽快”“相关”“等等”“部分”等模糊词；写具体名称、数量、版本和时间。

### 6.2 内容组织

1. 首段在 30 秒内说明：文档讲什么、给谁看、读者能获得什么。
2. 段落保持 3 至 5 句；比较和字段说明优先使用表格。
3. 操作步骤使用有序列表或代码块，必须能从仓库根目录或指定目录直接执行。
4. 命令示例要给出可验证的输出或检查方式，避免只写“应该成功”。
5. 涉及当前代码行为时写明版本、配置或代码路径，不使用“最近”“当前”代替。
6. 代码标识符、文件名、命令使用行内代码；代码块必须标注语言。
7. 需要图时优先使用 Mermaid；图片放入 `.docs/others/` 并使用有意义的替代文本。
8. 仓库内部引用使用相对路径链接；外部链接只在必要时出现，并注明访问日期或版本。

### 6.3 Markdown 格式

1. 文件使用 UTF-8 和 LF 换行。
2. 每个文件只有一个 H1；标题层级从 H2 开始，按顺序递增。
3. 使用 GFM 语法，不引入 HTML、内联样式或自定义渲染特性，除非 Markdown 无法表达。
4. 无序列表统一使用 `-`，有序步骤使用 `1. 2. 3.`。
5. 表格必须有表头和分隔行，单元格内容保持简短。
6. 建议每句一行，便于 review 和 Git diff 阅读；长表格按行维护。
7. 文件不得包含尾随空格；标题、代码块、表格前后保留空行。

## 7. 准确性与安全

1. 禁止提交任何密钥、口令、Token、证书、真实手机号、真实邮箱或个人隐私。
2. 敏感信息一律使用占位符，例如 `<token>`、`${DB_PASSWORD}`。
3. 不复制源码或表结构作为唯一事实来源；写“见 `xxx.java`”或“见 `xxx.sql`”并链接。
4. 接口文档优先由 OpenAPI/Knife4j 等工具生成；生成物必须标注“由工具生成，请勿手工编辑”并写明生成命令。
5. 文档中的命令、版本号和配置必须与当前代码一致；不一致视为文档缺陷。
6. 合并前检查所有相对链接和锚点；失效链接视为文档缺陷。
7. 废弃内容不直接删除历史；将状态改为“已废弃”并链接替代文档。

## 8. 评审与维护

### 8.1 生命周期

正式文档状态流转如下：

```text
草稿 -> 评审中 -> 已批准 -> 已废弃
```

1. 草稿允许在分支中演进，不直接合入主分支。
2. 已批准文档只能通过 PR 修改；修改必须同步更新状态、时间和变更历史。
3. 决策被替代或内容失效时，通过新 PR 标记为“已废弃”，并指明替代文档。
4. 负责人定期检查所属文档；至少每季度确认一次是否仍然准确。

### 8.2 评审要求

文档变更与代码变更同等对待：

1. 每份正式文档必须指定负责人，负责批准和维护。
2. 正式文档至少需要一名熟悉主题的评审人。
3. 修改文档的 PR 必须包含对应代码或配置变更的上下文。
4. 如果代码行为变化，同一 PR 中必须更新受影响的文档，否则视为未完成。

文档 PR 合并前检查：

```markdown
- [ ] 内容与当前代码、配置和运行环境一致
- [ ] 无密钥、Token、私钥、真实个人信息
- [ ] 相对链接和锚点可访问
- [ ] 元信息中的状态、负责人、更新时间已更新
- [ ] 没有与其他文档重复维护同一事实
- [ ] 命令可直接执行，示例结果可验证
- [ ] 已添加或更新变更历史
```

## 9. 模板

### 9.1 ADR 模板

```markdown
# ADR-XXX: 简短标题

| 属性 | 值 |
| --- | --- |
| 状态 | 提案中 |
| 负责人 | 模块 Owner |
| 创建时间 | YYYY-MM-DD |
| 更新时间 | YYYY-MM-DD |

## 背景

说明问题、约束和触发原因。

## 决策

### 1. 决策点

**选择**：最终方案。

**原因**：选择该方案的理由。

**备选**：考虑过但未选择的方案。

## 后果

说明正面影响、负面影响和后续维护责任。

## 待定

列出尚未决定或需要验证的事项。
```

### 9.2 开发手册模板

```markdown
# 主题使用指南

| 属性 | 值 |
| --- | --- |
| 状态 | 已批准 |
| 负责人 | 模块 Owner |
| 创建时间 | YYYY-MM-DD |
| 更新时间 | YYYY-MM-DD |

## 背景与目标

说明给谁看、解决什么问题。

## 前置条件

- 环境依赖
- 配置要求

## 操作步骤

1. 第一步
2. 第二步

## 验证

说明如何确认步骤生效。

## 相关文档

- [文档中心](../README.md)
```

### 9.3 运维 Runbook 模板

```markdown
# Runbook: 目标服务 故障场景

| 属性 | 值 |
| --- | --- |
| 状态 | 已批准 |
| 负责人 | Ops Owner |
| 创建时间 | YYYY-MM-DD |
| 更新时间 | YYYY-MM-DD |

## 症状

描述如何识别该故障。

## 影响

说明影响范围、严重级别。

## 处理步骤

按顺序给出可执行命令和判断条件。

## 恢复确认

说明如何确认服务恢复正常。

## 事后总结

记录根因、改进项和后续行动。
```
