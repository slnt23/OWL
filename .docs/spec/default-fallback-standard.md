## 背景与目标

项目规范不可能穷举所有场景。当某个具体操作或决策没有对应的显式规则时，必须有一套默认的保底行为来兜底，确保系统行为可预测、可维护，不会因为"规范没写"而出现随意发挥。

本文档定义 OWL 仓库中所有操作（编码、配置、数据库、文档、API 设计、异常处理等）的默认保底规则。当具体规范未覆盖某一场景时，以下规则即为最终依据。

## 核心原则

1. 宁可保守，不可冒险：不确定时选择最安全、最保守的方案。
2. 宁可显式，不可隐式：不确定时选择显式声明而非隐式推断。
3. 宁可简单，不可复杂：不确定时选择最简单的实现，复杂度留到确有必要时再引入。
4. 宁可失败可见，不可静默吞错：不确定时选择让错误可见而非静默忽略。
5. 宁可保持一致，不可另起炉灶：不确定时选择与现有代码风格一致的写法。

## 一、代码保底规则

### 1.1 异常处理

- 任何 `catch` 块禁止为空；至少记录日志并说明原因。
- 未预期的异常统一由 `GlobalExceptionHandler` 兜底，返回 `Result.fail("系统繁忙，请稍后再试")`。
- 外部调用（HTTP、RPC、MQ）必须设置超时时间，默认超时 30 秒；未配置超时视为缺陷。
- 异步任务必须配置异常处理器，未捕获异常不得导致线程池静默终止。

### 1.2 空值与边界

- 集合、数组、字符串在未确认非空时，必须先判空再操作。
- 数值计算前必须校验除数为零、溢出和精度丢失。
- 分页查询默认 `page=1, size=10`；未传分页参数时使用此默认值。
- 排序参数未传时使用 `id DESC` 作为默认排序。

### 1.3 并发与资源

- 所有资源（流、连接、文件句柄）必须使用 try-with-resources 或 finally 关闭。
- 共享状态操作（计数器、缓存写入、状态变更）默认考虑并发安全。
- 锁的持有时间默认不超过 5 秒；超时视为异常。

### 1.4 安全

- 所有用户输入默认不可信，必须经过校验和转义。
- 敏感数据（密码、Token、密钥）默认不输出到日志；日志级别为 DEBUG 时也不得输出。
- 接口默认要求登录认证；白名单必须显式声明。

## 二、数据库保底规则

### 2.1 表设计

- 所有表默认包含 `id`（主键）、`create_time`、`update_time` 三个字段。
- 逻辑删除优于物理删除；表默认包含 `is_deleted` 字段，默认值 `0`。
- 字符串字段默认使用 `utf8mb4` 字符集，排序规则 `utf8mb4_general_ci`。
- 未明确指定长度的字符串字段默认使用 `VARCHAR(255)`。

### 2.2 查询

- 所有查询默认分页；未指定分页大小的列表查询视为缺陷。
- 所有 UPDATE 和 DELETE 语句必须带 WHERE 条件；全表更新或删除禁止执行。
- 慢查询阈值默认 1 秒；超过此阈值必须记录日志并纳入优化计划。

### 2.3 索引

- 外键关联字段默认添加索引。
- WHERE 条件中频繁出现的字段默认添加索引。
- 单表索引数量默认不超过 5 个；超过时需要评审。

## 三、API 保底规则

### 3.1 请求与响应

- 所有接口统一返回 `Result<T>`；不直接返回裸对象或字符串。
- 请求体超过 1 MB 时默认拒绝；文件上传接口单独配置上限。
- 未指定 HTTP 方法的接口默认使用 POST。
- 路径参数必须做格式校验；未校验视为缺陷。

### 3.2 错误响应

- 业务错误统一使用 `ResultStatus` 中的业务状态码；不使用纯字符串错误信息。
- 参数校验失败统一返回 400 和具体字段错误，不返回 500。
- 下游服务不可用时默认返回 503，并设置合理的熔断和降级策略。

### 3.3 幂等性

- 写操作（POST、PUT、DELETE）默认要求幂等；重复提交不产生副作用。
- 支付、扣库存等关键操作必须实现幂等；未实现不得上线。

## 四、配置保底规则

### 4.1 环境配置

- 所有可配置项必须有默认值；未配置时不报错、不阻塞启动。
- 敏感配置（密码、密钥）默认从环境变量或 Nacos 读取；不硬编码到文件中。
- 开发环境默认使用 `dev` profile；生产环境默认使用 `prod` profile。

### 4.2 超时与重试

- 网络请求默认超时 30 秒，连接超时默认 10 秒。
- 重试默认最多 3 次，间隔采用指数退避（1s、2s、4s）。
- 消息消费失败默认重试 3 次后进入死信队列。

### 4.3 日志

- 日志级别默认 INFO；生产环境禁止 DEBUG 或 TRACE。
- 关键操作（登录、支付、权限变更、数据删除）默认记录 INFO 级别日志。
- 日志文件默认按天滚动，保留 30 天。

## 五、文档保底规则

### 5.1 内容

- 新增模块默认需要一份 README 说明用途、依赖和启动方式。
- 接口变更默认同步更新 OpenAPI 文档。
- 配置项变更默认在对应配置文件中添加注释说明。

### 5.2 评审

- 所有 PR 默认需要至少一人评审。
- 涉及数据库变更的 PR 默认附带 DDL 脚本。
- 涉及接口变更的 PR 默认附带接口文档更新。

## 六、模块开发保底规则

### 6.1 新增模块

- 新模块默认放在 `watermelon/` 下，遵循 `{业务名}` 命名。
- 新模块默认依赖 `api` 模块，复用统一返回、认证和日志能力。
- 新模块的 Controller 默认放在 `{模块}/controller` 包下，Service 放在 `{模块}/service` 包下。

### 6.2 公共能力

- 两个以上模块复用的代码默认抽取到 `common`、`infra`、`log` 或 `api`。
- 不确定归属的公共能力默认放在 `common` 模块。

## 七、测试保底规则

### 7.1 覆盖

- 核心业务逻辑（支付、认证、权限）默认需要单元测试。
- 公共工具类方法默认需要单元测试。
- 新增接口默认需要至少一个集成测试用例。

### 7.2 数据

- 测试数据默认使用随机生成，不依赖特定数据库状态。
- 测试完成后默认清理测试数据，不残留。

## 八、决策优先级

当某一场景同时被具体规范和本保底规范覆盖时，具体规范优先。当具体规范未覆盖时，按以下优先级依次适用：

1. 本保底规范中的对应规则。
2. 核心原则中的五条原则。
3. 与现有代码库中最相似场景保持一致。
4. 选择业界通用最佳实践。

如以上均无法确定，必须在代码中添加 `TODO(负责人): 待确认方案` 并在 PR 中说明，不得自行决定后合入。
